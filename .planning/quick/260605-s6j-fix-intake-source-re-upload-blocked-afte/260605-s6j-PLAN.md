# Quick Task Plan: Fix intake source re-upload blocked after soft-delete

**Quick ID:** 260605-s6j  
**Description:** Fix intake source re-upload blocked after soft-delete: deleted intake items still block re-upload due to sha256 unique constraint and repository query not excluding deleted sources.

## Root Cause

1. `IntakeRepository.get_by_sha256()` queries `SELECT * FROM intake_sources WHERE sha256 = ? LIMIT 1` without filtering out `status = 'deleted'`. This causes the application-level duplicate check to reject re-uploads even after soft-delete.
2. The `intake_sources` table has a `UNIQUE(sha256)` constraint (migration 018). Since soft-delete preserves the row, the DB-level constraint also blocks re-insertion of the same file hash.
3. Bank inputs do not share this bug because they are hard-deleted; the row and constraint are removed on delete.

## Tasks

### Task 1: Fix repository query to exclude deleted sources
- **File:** `repositories/intake_repo.py`
- **Action:** Change `get_by_sha256()` to add `AND status != 'deleted'` to the WHERE clause.
- **Verify:** The method returns `None` when only a deleted source has the matching sha256.

### Task 2: Replace full unique constraint with partial unique index
- **File:** `db/migrations/021_allow_reupload_deleted_intake_sources.sql`
- **Action:** Create migration that recreates `intake_sources` without the inline `UNIQUE(sha256)`, adds a partial unique index `UNIQUE(sha256) WHERE status != 'deleted'`, and preserves all existing data including the `agent_guidance` column.
- **Verify:** Migration applies cleanly to existing databases and new partial index prevents duplicate active sources while allowing re-upload after soft-delete.

### Task 3: Add regression test
- **File:** `tests/test_intake_api.py`
- **Action:** Add `test_intake_service_allows_reupload_after_soft_delete` that uploads a file, soft-deletes it, then re-uploads the same bytes successfully.
- **Verify:** Test passes and existing duplicate-rejection test still passes.
