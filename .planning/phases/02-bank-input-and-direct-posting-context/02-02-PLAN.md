<objective>
As a user, I want a parseable uploaded bank CSV to immediately import transaction rows while preserving the original CSV and processing counts, so that the agent can use bank input as structured source material instead of a loose file.
</objective>

<context>
This plan builds on Plan 02-01 storage/API. It keeps transaction persistence inside `BankIntegrationService` but adds known-format detection and enough result detail for `BankInputService` to link imported rows back to the uploaded file.
</context>

<threat_model>
**Assets:** original CSV files, imported bank transactions, duplicate-detection keys, bank input lifecycle and counts.

**Threats:**
- HIGH: unknown CSV formats silently import zero or malformed transactions.
- HIGH: duplicate rows or repeated uploads create duplicate bank transactions.
- MEDIUM: imported transactions cannot be traced back to the uploaded CSV.
- MEDIUM: partial import failure leaves bank input status inconsistent with transaction rows.

**Required mitigations:**
- Unknown header mappings must mark `bank_inputs.status = 'failed'` with a clear `parse_error`.
- Continue duplicate detection through `(bank_connection_id, external_id)`.
- Record imported and skipped counts on every processed/failed bank input.
- Link every imported transaction row to `bank_input_transactions`.
</threat_model>

<must_haves>
<truths>
- D-04: duplicate transaction rows inside an uploaded CSV are skipped while the rest of the upload is processed; imported and skipped counts are preserved.
- D-06: CSV parsing auto-detects the format from a known list of supported bank formats.
- D-07: unknown CSV format marks the bank input `failed` with a clear parsing error.
- D-08: successful CSV upload immediately imports transactions and records imported/skipped counts.
- BANK-03: imported rows are created through existing bank import logic rather than a separate table-only parser.
</truths>
</must_haves>
