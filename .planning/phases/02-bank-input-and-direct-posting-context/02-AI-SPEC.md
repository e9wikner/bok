## 1. System Classification

**System Type:** Autonomous Agent Tool Contract / Backend Guardrail Surface

**Description:**
Phase 2 does not embed an LLM runtime inside Bok. It extends Bok's existing FastAPI agent-facing API so an external bookkeeping agent can use bank CSV inputs, imported bank transactions, voucher source material, invoices, payroll references, existing vouchers, and correction history to decide which missing vouchers to post. "Good" means the backend gives the agent complete, typed, traceable context and rejects unsafe tool calls while still allowing automation-first direct posting through the existing ledger validation path.

**Critical Failure Modes:**
1. The agent posts a bank-driven voucher using a bank transaction that is already `booked` or has `matched_voucher_id`.
2. A posted voucher created from bank input cannot be traced back to the uploaded bank CSV and the specific imported transaction rows used.
3. The pending agent queue conflates voucher sources and bank inputs so the agent loses source type, download, or transaction linkage semantics.
4. Correction history is omitted from the agent context, causing repeated accounting mistakes after user corrections.
5. CSV import failures or duplicate rows are hidden from the agent/user instead of being recorded as explicit processing results.

## 1b. Domain Context

> Researched inline by the orchestrator. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Swedish small-company bookkeeping / finance

**User Population:** Owners or operators of Swedish aktiebolag using Bok without an external accountant, plus an external accounting agent consuming Bok's API.

**Stakes Level:** High

**Output Consequence:** Agent tool calls create immutable posted vouchers. Mistakes are corrected through B-series correction vouchers, so bad decisions add audit-visible correction work rather than being edited away.

### What Domain Experts Evaluate Against

| Dimension | Good (expert accepts) | Bad (expert flags) | Stakes | Source |
|-----------|-----------------------|--------------------|--------|--------|

| Duplicate prevention | Backend blocks explicit reuse of `booked` or matched transactions before posting. | Same bank movement can be posted twice through repeated agent calls. | Financial statement correctness. | Phase 2 D-15/D-16 |

### Known Failure Modes in This Domain

1. Bank transactions with generic descriptions such as card purchases are booked without matching receipt/invoice source material.
2. A payment transaction is mistaken for an expense or sale instead of settlement of an existing invoice.
3. Payroll or tax payments are booked as ordinary expenses instead of linked to payroll/tax context.
4. Agent repeats a corrected account choice because correction history was not included or not visible near the relevant source context.
5. Duplicate CSV rows, repeated uploads, or retried agent calls create duplicate vouchers.

### Regulatory / Compliance Context

- Posted vouchers are immutable in this project; corrections must be new B-series correction vouchers.
- Traceability from voucher to source material is a project requirement for audit and user review.
- The backend, not the agent, remains responsible for formal accounting constraints: balanced rows, valid periods, active accounts, posted-voucher immutability, and transaction reuse rejection.
- File-serving paths must remain constrained to the configured storage root.

### Domain Expert Roles for Evaluation

| Role | Responsibility |
|------|---------------|
| Swedish bookkeeping practitioner | Review reference cases, label expected voucher/source/transaction links, calibrate correction-history rubric. |
| Bok maintainer | Encode deterministic backend guardrails and regression tests for tool calls. |
| Small-company operator | Spot-check whether failed/processed statuses and agent summaries are understandable after the fact. |

## 2. Framework Decision

**Selected Framework:** Direct FastAPI + Pydantic tool contract, with no in-process AI orchestration framework for Phase 2

**Version:** FastAPI `>=0.109.0`, Pydantic `>=2.6.0`, pytest `7.4.3`

**Rationale:**
Phase 2 is backend enablement for an external agent, not a new embedded LLM workflow. The work needs strict request/response schemas, explicit source links, transaction reuse validation, and deterministic tests. Adding LangGraph, OpenAI Agents SDK, CrewAI, or another orchestration framework would increase surface area without solving the phase goal. The correct design is to expose typed API tools and context packages that any external agent can consume, while Bok enforces non-negotiable accounting and traceability constraints.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| LangGraph | Useful for stateful agent orchestration, but Bok is not hosting the agent loop in Phase 2. The state that matters is already persisted in SQLite through domain tables. |
| OpenAI Agents SDK | Good for OpenAI-hosted agents, but Phase 2 should remain provider-neutral and backend-focused. |
| CrewAI | Multi-agent role orchestration is unrelated to bank input upload, transaction import, and posting safeguards. |
| LlamaIndex | Retrieval is not the bottleneck; Phase 2 uses structured SQL context and file/source links rather than semantic document search. |

**Vendor Lock-In Accepted:** No. The backend API contract should remain model/provider agnostic.

### Common Pitfalls

1. Treating "agent context" as free-form text instead of a typed API payload with IDs the backend can validate.
2. Letting the agent infer duplicate status without backend rejection of already booked/matched bank transactions.
3. Adding a new agent posting path that bypasses `LedgerService.create_voucher` and `LedgerService.post_voucher`.
4. Returning every transaction row inline in the pending queue; Phase 2 requires compact summaries plus linked transaction IDs.
5. Losing the original uploaded CSV after import; BANK-02 requires preserving the uploaded file and metadata.

## 4. Implementation Guidance

**Model Configuration:**
No model is configured inside Bok for Phase 2. The external agent may use any provider/model, but Bok must expose deterministic JSON schemas and enforce all hard constraints server-side.

**Core Pattern:**
Use FastAPI route handlers as thin adapters over service methods. Service methods perform upload validation, CSV format detection, transaction import, pending queue assembly, bank transaction availability checks, voucher/source linking, and status updates inside SQLite transactions where state must change atomically.

**Tool Use:**
The external agent's relevant tools are backend endpoints:
- `GET /api/v1/agent/intake/pending` returns typed `kind` items: `voucher_source` and `bank_input`.
- `GET /api/v1/accounting-corrections` returns correction history for learning context.
- `POST /api/v1/agent/vouchers` accepts ordinary voucher rows plus optional `bank_input_ids`, `bank_transaction_ids`, and `intake_source_ids`.
- Human upload APIs accept CSV bank inputs against a selected existing `bank_connection_id`.

**State Management:**
SQLite remains the source of truth. Bank input records preserve original file metadata, lifecycle, parse errors, import counts, and storage path. Link tables preserve voucher-to-bank-input and voucher-to-bank-transaction traceability. Used bank transactions transition to `booked` and receive `matched_voucher_id` only after successful voucher posting.

**Context Window Strategy:**
Keep agent queue responses compact. Bank input items should include status, file metadata, import counts, parse error if any, bank connection summary, and transaction IDs/counts. Full transaction detail should be fetched through focused endpoints or included only in bounded context packages, not sprayed into every queue response.

## 4b. AI Systems Best Practices

> Cross-cutting patterns for this provider-neutral agent API.

### Structured Outputs with Pydantic

Use Pydantic to define the exact agent tool-call schema. Validation failures should return stable `detail.code` values so the external agent can correct input rather than guessing.

```python
from datetime import date
from pydantic import BaseModel, Field, model_validator

class AgentBankVoucherRequest(BaseModel):
    date: date
    period_id: str
    description: str = Field(..., min_length=1)
    rows: list[VoucherRowRequest] = Field(..., min_length=2)
    reasoning_summary: str | None = None
    bank_input_ids: list[str] = Field(default_factory=list)
    bank_transaction_ids: list[str] = Field(default_factory=list)
    intake_source_ids: list[str] = Field(default_factory=list)

    @model_validator(mode="after")
    def require_bank_traceability(self):
        if self.bank_input_ids and not self.bank_transaction_ids:
            raise ValueError("bank_input_ids require bank_transaction_ids")
        return self
```

Retry policy belongs outside Bok. Bok should return precise 400/409 codes such as `bank_transaction_already_booked`, `bank_input_not_found`, `unsupported_bank_csv_format`, and `duplicate_bank_input`.

### Async-First Design

Keep FastAPI endpoints async-compatible, but avoid pretending local filesystem writes and SQLite calls are non-blocking. The existing codebase uses synchronous services behind async route handlers; Phase 2 should follow that pattern unless a broader storage/database refactor is planned.

### Prompt Engineering Discipline

Do not place model prompts in this phase. The backend should provide context fields that are useful for prompts: source kind, source IDs, transaction IDs, correction history entries, candidate duplicate/match signals, and prior voucher references. The external agent's prompt should treat backend rejection codes as authoritative constraints.

### Context Window Management

Expose summaries and IDs first, detail on demand. Correction history should be available in full for Phase 2 per D-12, but route design should still allow future filtering by voucher, date range, account, counterparty, or source type.

### Cost and Latency Budget

Backend overhead should be dominated by SQLite queries and CSV parsing, not LLM calls. Agent context endpoints should use bounded `limit`/`offset` parameters and avoid N+1 hydration of full vouchers/transactions in queue listings.

## 6. Guardrails

### Online (Real-Time)

| Guardrail | Trigger | Intervention |
|-----------|---------|--------------|
| Transaction already booked | Supplied transaction has `status = 'booked'` or `matched_voucher_id IS NOT NULL`. | Block with 409 before voucher creation. |
| Missing bank traceability | Request supplies bank input IDs without transaction IDs, or transaction IDs not linked to supplied bank input. | Block with 400/409. |
| Ledger validation failure | Voucher rows are unbalanced, account invalid, or period locked/invalid. | Block through existing `LedgerService` validation. |
| CSV format unknown | Bank input upload cannot be mapped to a known supported format. | Mark bank input `failed`, store parse error, do not import transactions. |
| File outside storage root | Download path resolves outside configured bank/intake root. | Block with 403. |

### Offline (Flywheel)

| Metric | Sampling Strategy | Action on Degradation |
|--------|-------------------|-----------------------|
| Correction rate for agent-posted bank vouchers | Review all B-series corrections linked to agent-created vouchers. | Add/adjust agent instructions and reference examples. |
| Duplicate-post prevention hits | Count 409 `bank_transaction_already_booked` and matched-transaction rejections. | Inspect whether context is missing existing-match signals. |
| Failed bank input uploads | Sample all `failed` bank inputs weekly. | Add supported CSV formats or improve error messages. |
| Unbooked pending bank transactions age | Sample pending transactions older than 30 days. | Improve queue prioritization or context package. |

## 7. Production Monitoring

**Tracing Tool:** Arize Phoenix is the default future trace target for external agent tool-call traces. Phase 2 implementation should at minimum preserve backend audit data in SQLite; no Phoenix runtime dependency is required for this phase.

**Key Metrics to Track:**
- Count of bank inputs by status: `pending`, `processed`, `failed`.
- Imported/skipped transaction counts per bank input.
- Agent-posted vouchers with linked bank inputs and transaction rows.
- Rejected agent voucher attempts by stable error code.
- B-series corrections linked to agent-created vouchers.

**Alert Thresholds:**
- Any successful bank-driven voucher missing a bank input or bank transaction link is a critical defect.
- Any duplicate transaction reuse that results in a posted voucher is a critical defect.
- More than 20% failed bank inputs over the last 20 uploads should trigger CSV format review.
- Any storage-root containment failure should trigger security review.

**Smart Sampling Strategy:**
Review all critical guardrail failures, all agent-created vouchers later corrected by B-series voucher, all failed bank inputs, and a rotating sample of successful bank-driven postings that involve multiple transaction rows or invoice/payroll-like descriptions.
