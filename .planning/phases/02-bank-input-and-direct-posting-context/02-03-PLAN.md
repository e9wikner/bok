<objective>
As an accounting agent, I want typed bank input context, correction history, and guarded bank-driven voucher posting, so that I can post missing vouchers directly while the backend prevents duplicate transaction reuse and preserves source traceability.
</objective>

<context>
This plan completes Phase 2 by extending the existing agent surface. It must keep voucher creation on `LedgerService.create_voucher` and `LedgerService.post_voucher`, then add bank/source links and transaction status updates only after successful posting.
</context>

<threat_model>
**Assets:** posted vouchers, imported bank transactions, uploaded bank input files, ordinary voucher source links, correction history, agent context payload.

**Threats:**
- HIGH: an agent reuses a `booked` or matched bank transaction and creates duplicate accounting.
- HIGH: a bank-driven voucher posts without durable links to the bank input and transaction rows used.
- HIGH: a new agent posting path bypasses ledger validation, period locks, account validation, or posted-voucher immutability rules.
- MEDIUM: queue item shape conflates voucher sources and bank inputs, leading the agent to lose source semantics.
- MEDIUM: correction history is omitted, causing repeated errors after user correction.

**Required mitigations:**
- Preflight every supplied `bank_transaction_id` and reject `status='booked'` or non-null `matched_voucher_id` with HTTP 409 before voucher creation.
- Verify every supplied transaction belongs to one of the supplied bank inputs.
- Use `LedgerService.create_voucher` and `LedgerService.post_voucher` unchanged for formal posting.
- After successful posting, create voucher-bank traceability links and mark used transactions `booked` with `matched_voucher_id`.
- Extend queue response with explicit `kind` and type-specific fields.
</threat_model>

<must_haves>
<truths>
- D-09: bank inputs appear in the existing agent pending queue while remaining a separate model.
- D-10: shared queue items include `kind` values `voucher_source` and `bank_input`.
- D-11: bank input queue entries include compact summary fields and linked transaction IDs, not every transaction row inline.
- D-12: full correction history is exposed to the agent.
- D-13: duplicate/match candidates are surfaced, but the agent decides whether to post for inferred matches.
- D-14: Phase 2 match surfacing is limited to bank transaction status and `matched_voucher_id` signals.
- D-15: explicit reuse of a booked or matched bank transaction is rejected by the backend.
- D-16: successful bank-driven posting marks used bank transactions `booked` and sets `matched_voucher_id`.
- D-17: every bank-driven voucher links to the uploaded bank input and exact bank transaction rows used.
- D-18: one voucher may use multiple bank transaction rows.
- D-19: one bank input CSV may lead to multiple vouchers over time.
- D-20: bank-driven posting can also link ordinary voucher intake sources.
</truths>
</must_haves>
