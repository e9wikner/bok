<objective>
As a user and agent, I want authenticated intake APIs for upload, download, pending queue listing, and processing outcome recording, so that source material can be handed to the agent without manual voucher pre-creation.
</objective>

<context>
This plan exposes the service from Plan 01-01 through FastAPI. It adds the human upload/download surface and the agent queue/outcome surface, but it does not yet link posted vouchers to intake sources; that is Plan 01-03.
</context>

<threat_model>
**Assets:** original uploaded source files, pending queue metadata, processing attempt details.

**Threats:**
- HIGH: unauthenticated download of financial source files.
- HIGH: path traversal or DB-tampered file path leaks arbitrary process-readable files.
- MEDIUM: agent marks unsupported statuses and corrupts Phase 1 lifecycle.
- MEDIUM: deleted or processed items remain visible in the pending queue.

**Required mitigations:**
- Every new endpoint must depend on `get_current_actor`.
- `GET /api/v1/intake/{id}/file` must use `IntakeService.resolve_source_file` and never serve raw DB paths without containment checks.
- Agent outcome API in Phase 1 may set only `processing`, `processed`, or `failed`; `skipped` and `needs_attention` are table lifecycle values but not accepted agent outcomes yet.
- Pending queue must filter to `status='pending'`.
</threat_model>

<must_haves>
<truths>
- D-07: pending intake items can be soft-deleted and must be hidden from the agent pending queue.
- D-08: no explicit claim step; items remain pending until the agent records a processing outcome.
- D-10: agent outcome API can set only `processed` or `failed` in Phase 1, with `processing` allowed only as a transient attempt marker.
- D-11: failed processing attempts require a short summary and error detail.
- D-12: pending queue responses include authenticated download URLs.
- D-13: use stable authenticated endpoint `/api/v1/intake/{id}/file`.
- D-15: downloads reject paths outside the configured root.
</truths>
</must_haves>
