**Status:** SHIPPED 2026-06-05

## Overview

Make a deployed Bok instance understandable and connectable for an OpenClaw-style HTTP agent so it can begin bookkeeping through the existing agent API.

## Milestone Summary

**Key Decisions:**

- Entrypoint returns only static metadata and `settings.api_version`; it does not use auth dependencies or repositories.
- Entrypoint uses relative paths only and links `/openapi.json` as the canonical generated schema.
- Removed misleading placeholder routes instead of deprecating them.
- Ping returns only status, service, configured version, authenticated actor, and current UTC timestamp.
- LAN-first agent setup with `BOK_API_URL` and `API_KEY` shell variables avoids inline secrets in docs.
- First agent instruction is setup-only: verifies access, reports readiness, asks owner before bookkeeping.
- Deployment docs verify with `pathlib.Path` + pytest assertions, not manual review.

**Issues Resolved:**

- Existing synchronous TestClient requests hung under the current Python/runtime combination; fixed by converting to async ASGI transport.
- Date-sensitive correction workflow test created a May 2026 period but corrections were dated to June; fixed by creating a period for the current month.
- README and agent routes contained stale placeholder-route references; cleaned up to point to the entrypoint startup flow.

**Issues Deferred:**

- Phase 1 aggregate `01-VERIFICATION.md` missing (deferred from v1.0, still open).
- v1.1 milestone audit and Phase 5 security review not run (deferred from v1.1, still open).

**Technical Debt Incurred:**

- 6 v1.2 requirements (AUTH-01, DOCS-01-04, VER-02) had stale unchecked boxes in REQUIREMENTS.md even though they were completed in Phase 7. The phase SUMMARY.md files correctly recorded completion, but the top-level requirements checkboxes were not synced during execution. This is a process gap in requirements traceability maintenance.
